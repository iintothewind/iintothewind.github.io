      omp 官方文档高效读取方法（实测版）

      写给自己和其他 agent 复用。目标：读 omp.sh/docs 时少花 token、少踩坑。 实测时间：2026-09。所有 URL 都 curl/jina 验证过，状态码和字节数写进去，踩过的坑也标了。 背景：omp = oh-my-pi（作者 can1357），一个把 IDE 接进来的 coding agent。

      TL;DR

      一句话：omp 的文档站是 JS 重度渲染的 Mintlify 站，直接 curl 拿到的几乎是空壳——但它的 .md 单页形态是全套 agent 友好方案里最省事的：任意页加 .md 后缀就返回干净 Markdown。没有 llms-full.txt 全文、没有 MCP server、没有官方 skill，别指望 TypeSafe 那套全配置。

      效率排序：

      <页面URL>.md (单页)   >   /llms.txt (全站索引)   >>   /llms-full.txt (名存实亡)   >   爬 HTML
      • 读单篇 → <页面URL>.md（任意页加 .md 后缀返回干净 Markdown）
      • 找哪一页 → /llms.txt（目录索引，每页路径不带 .md，自己拼）
      • 直连失败 → 用 jina（unifetch），站点被 bot 拦截

      三种形态（都实测）

      形态 URL 状态 用途
      Markdown 单页 <页面URL>.md ✅ 200, text/markdown 取单篇正文（主力）
      全站索引 /llms.txt ✅ 200, text/plain 目录页，路径不带 .md
      聚合全文 /llms-full.txt ⚠️ 名存实亡 只返回索引 + "Page not found"，别依赖
      HTML 页 <页面URL> ❌ 直连 0KB JS 渲染，curl/web_fetch 拿空壳

      ⚠️ 和 TypeSafe 的关键区别：TypeSafe 有 llms-full.txt（874KB 全文）+ MCP server + agent skill 四件套；omp 只有 .md + llms.txt，llms-full.txt 实际不存在全文。别按 TypeSafe 的经验去抓全文。

      为什么直连拿不到

      omp 的文档站是 JS 重度渲染的 Mintlify 站。直接 curl https://omp.sh/docs/quickstart 或 web_fetch，返回的正文几乎是空的——只有 Skip to content 这类导航占位，正文要等前端 JS 跑出来才有。所以：

      curl -s https://omp.sh/docs/quickstart
# → 几乎空，正文被 JS 渲染挡住，拿不到

      解法：用 jina（unifetch 的 jina 后端），它替你跑渲染。unifetch.sh read 走 jina，能拿到干净正文：

      bash ~/.zeroclaw/shared/skills/infra/unifetch/scripts/unifetch.sh read 'https://omp.sh/docs/quickstart'
# → [unifetch] jina: ok，返回干净 Markdown

      URL 模式（精确，可直接粘）

      1. 单页 Markdown（最常用，主力）

      # 任意页面加 .md 后缀
curl -s https://omp.sh/docs/quickstart.md
# → 200, text/markdown，干净正文（表格、链接都在）

# 嵌套路径同理
curl -s https://omp.sh/docs/tools.md
curl -s https://omp.sh/docs/session-format.md

      实测 quickstart.md 返回的就是完整文档（Overview / Capabilities / Models / Customization 等全在）。这是 omp 唯一可靠的全文取页方式。

      2. 全站索引（先读它再挑页）

      curl -s https://omp.sh/docs/llms.txt
# → ~80 行目录，每行：* [标题](https://omp.sh/docs/<path>)
# 注意：链接里**不带 .md**，自己拼 .md 再去取
# 覆盖：Start / Capabilities / Models / Customization / Programmatic /
#       Using omp / Slash / Keybindings / Settings / Modes / Sessions /
#       Tools / CLI / env / secrets / approvals / session-format

      3. 聚合全文（试了，别依赖）

      curl -s https://omp.sh/docs/llms-full.txt
# → 实测只返回 llms.txt 索引 + 末尾 "Page not found"
# 并不是全站正文合并（不像 TypeSafe 的 874KB 全文）

      Agent 工作流

      读某一篇文档（最常见）：

      1. curl -s https://omp.sh/docs/llms.txt → 从目录里挑目标页
      2. curl -s https://omp.sh/docs/<目标页>.md → 拿干净 Markdown，直接进上下文

      直连被挡时：

      • 别硬 curl HTML。用 jina 后端：unifetch.sh read 'https://omp.sh/docs/<页>'
      • .md 后缀走 jina 也成立，二选一

      要建本地索引：

      • 抓 llms.txt 拿全部路径
      • 逐个拼 .md 下载，grep / 切片喂模型（没有更快的整站全文可用）

      工具怎么选

      工具 用在哪
      curl + .md 后缀 首选。任意页 Markdown，零解析、零 JS
      curl + /llms.txt 拿目录，挑页用
      jina / unifetch.sh read 直连被挡时的兜底（跑渲染）
      web_fetch 兼容 .md URL（本质普通 GET），但 curl 更直接
      无头浏览器（obscura） 不需要。.md 是静态响应
      MCP server / 官方 skill 没有。omp 未提供

      常见误区

      1. 别去抓 llms-full.txt 当全文：它返回的是索引 + "Page not found"，不是全站正文。omp 没有 TypeSafe 那种整站全文文件。
      2. llms.txt 的链接不带 .md：要去 .md，得自己拼。和 TypeSafe（链接自带 .md）不一样。
      3. 直连 HTML 拿空壳不是 bug 是设计：Mintlify JS 渲染，curl/web_fetch 拿不到正文，换 .md 或 jina。
      4. 别等官方 MCP / skill：omp 目前只给了 .md + llms.txt 两件套，agent 集成要靠 curl 自己拼。

      来源：omp.sh/docs（实测 2026-09）。Mintlify 站点，agent 友好形态目前是单页 .md + /llms.txt 两件套；llms-full.txt 名存实亡，无 MCP/skill。对比 TypeSafe 的四件套，omp 属于"够用但不全"。
