      让 agent 稳定读完长文：脚本分流 + file_read 分页

      一个 skill 设计笔记。场景：用 bash 脚本抓某个论坛帖子的正文，交给 agent 展示给用户。帖长从几百字到上万字不等，短帖要直接可读，长帖要能完整读到。

      以下全部数字来自实测（Windows/MSYS，Rust 运行时）。

      1. 问题：工具输出上限按字节算

      运行时会对每一次工具调用的返回值做截断：

      // 单次工具结果的硬上限
let original_bytes = output.len();          // Rust str::len() = 字节
let head_len = max_chars * 2 / 3;
let tail_len = max_chars.saturating_sub(head_len);
// 输出：头 2/3 + "[... N characters truncated ...]" + 尾 1/3

      两个容易踩的点：

      1. 单位是字节，标记里却写 "characters"。 中文 3 字节/字，max_tool_result_chars = 8000 实际只有约 2600 个汉字。
      2. 截断方式是「头 + 尾」，中间整段丢弃。 对正文类内容，这等于什么都拿不到——头是免责声明，尾是评论区。

      实测：一篇 15491 字节的帖子，在 8000 上限下被砍掉 7495 字节（正文第 13–23 段全部消失），agent 拿到的头尾拼起来无法阅读。

      7495 是截断标记里报告的实测值，不是用 15491 − 8000 = 7491 算出来的。差的 4 字节是两端按 UTF-8 字符边界对齐时的取整代价——8000 只是上限，不是实际保留量。运行时内部具体怎么取整，脚本侧不需要复算：分流阈值按字节量体积、再留 RESERVE，就是为了不依赖这种内部会计。

      2. 三种错误做法

      2.1 让脚本自己分页（--offset / --limit）

      第一反应是给抓取脚本加翻页参数。不要这样做：

      • file_read 本来就支持 offset / limit，并输出行号与 [Lines 12-34 of 230] 尾注；
      • 每个 skill 各写一套分页，等于重复实现运行时已有的能力；
      • 不通用——同一个 agent 还要读 md / pdf / csv，那些文件不可能都有配套的分页脚本。

      结论：分页属于通用读文件工具，不属于内容抓取脚本。

      2.2 调大全局上限

      把 max_tool_result_chars 从 8000 调到 80000 看起来能一劳永逸。代价：

      • 影响所有工具的输出，不只是长文；
      • 不解决根本问题：一篇 3 万字的帖子照样超；
      • 抬高了每轮 prefill 成本——一次误读就是几十 KB 灌进上下文；
      • 对「模型复读」这类问题毫无帮助（复读由工具调用模式检测和迭代上限控制，与输出体积无关）。

      合理做法是调到「覆盖绝大多数正常内容」即可（本例 8000 → 12000，仍远低于运行时默认的 50000）。

      2.3 只告诉 agent「分页读」

      给 SKILL.md 写「长文用 file_read 分页读」不够。实测观察到：

      file_read offset=1 limit=100
第 1 页（1-100）。读第 2 页。
file_read offset=101 limit=100
第 2 页（101-200）。读第 3 页。
file_read offset=201 limit=100
全部读完（230 行）。内容如下：<一次性贴出>

      模型把三条 file_read 读成一个连续动作序列，攒到最后才输出。用户在前两轮里什么都看不到。

      3. 做法：脚本量体积后分流

      脚本不再决定「分不分页」，只决定「这次要不要把正文放进 stdout」：

      # 缓存内容就是最终输出
size="$(wc -c < "$CACHE" | tr -d ' ')"

INLINE_MAX="${POST_INLINE_MAX:-12000}"   # 与运行时上限对齐，可用环境变量覆盖
RESERVE=256                              # 给工具层的包装文本留余量

if (( size + RESERVE <= INLINE_MAX )); then
  cat "$CACHE"
else
  echo "path:  $CACHE"
  echo "lines: $(wc -l < "$CACHE" | tr -d ' ')"
  echo "bytes: ${size}  (over the ${INLINE_MAX}-byte inline limit)"
  echo "read:  file_read path=$CACHE offset=1 limit=100"
fi

      三个设计要点：

      要点 理由
      阈值 ≤ 运行时上限 否则「直出」分支一样会被截断，分流就失效了
      留 RESERVE 工具层可能把 stderr、包装文本折进结果，实测留 256 字节够用
      RESERVE 的稳定性 它是运行时包装格式的函数：哪天运行时改了包装（比如把 stderr 折进来），分流阈值会静默失效。验证清单里加一条「每次升级运行时后重测包装开销」，或让脚本动态量包装大小而不是写死 256
      阈值可用环境变量覆盖 运行时的 max_tool_result_chars 改了以后，脚本侧不用改代码

      分流效果（5 个真实样本）：

      帖子大小 分支
      1.2 KB / 4.7 KB / 4.8 KB 直出（一次工具调用拿到全文）
      13.5 KB / 15.5 KB 只给路径（第二次调用 file_read 分页）

      短帖不额外付出一次读文件的开销，长帖不再出现「先被截断、再重读」的浪费。

      4. 关键细节：缓存必须等于最终输出

      最初的实现把标题存成哨兵：

      printf '\037TITLE:%s\037\n' "$t" > "$TMP/lines.txt"   # 后续用 awk 解析

      问题：file_read 直接读缓存时会看到 \x1fTITLE:...\x1f 这样的控制字符，与 stdout 不一致——agent 分页读到的第一行是乱码。

      改成写普通 markdown 标题行：

      : > "$TMP/lines.txt"            # 先清空，避免重跑时残留旧内容
if [[ -n "$t" ]]; then printf '# %s\n\n' "$t" >> "$TMP/lines.txt"; fi

      于是 stdout == cache，可以用 diff 直接验证：

      ./extract.sh '<url>' > /tmp/stdout.txt
diff /tmp/stdout.txt /tmp/cache_t<id>.txt && echo "identical"

      这条不变式带来三个好处：

      • agent 用 file_read 读缓存，看到的与脚本直出完全一致；
      • 不需要在显示层再写一遍解析/渲染逻辑（原实现有一段 awk 专门还原哨兵，删掉后渲染从 3 段缩成 1 段）；
      • 用户与 agent 看到同一份内容，排障时不会互相矛盾。

      5. SKILL.md：面向小参数模型

      compact 注入模式下，SKILL.md 正文不进 system prompt，只在 agent 调 read_skill 时整份读入。所以长度不是主要矛盾，结构清晰度才是。对小模型有效的几点：

      5.1 一步一个动作，一步一个判断

      第 1 步 跑命令
第 2 步 看输出第一行，二选一：
        - 不是 path: 开头 → 原样贴给用户，结束
        - 是 path: 开头   → 走第 3 步
第 3 步 按 read: 那行读第 1 页 → 读完立刻贴出 → 再读下一页
第 4 步 尾注右边界等于总行数 → 停止

      分支条件用第一行的字面前缀（path:），不要让模型做语义判断。

      5.2 给错误示范，不只给正确做法

      只写正确流程时，小模型会自行简化。把实际观测到的错误行为原样写进文档：

      错误示范（读完所有页才输出一次，用户中途什么都看不到）：

```
file_read offset=1 limit=100
第 1 页（1-100）。读第 2 页。
file_read offset=101 limit=100
第 2 页（101-200）。读第 3 页。
全部读完（230 行）。内容如下：<一次性贴出>
```

      这是本次唯一真正修掉「批量读完再输出」的手段。

      关于模型：Qwen9B 是我用来照顾的模型下限，不是随便挑的测试对象。再往下（更低参数量、更低量化）的模型，只能跑起来，我不期待它们能稳定遵守多步流程；Qwen9B 以上的模型（更大参数量、在线模型）只会效果更好。所以这条经验的适用范围是：Qwen9B 及以上。如果在某个模型上压不住，先检查模型是否在 Qwen9B 的能力范围之内，以及它是否遵守了 SKILL.md 的编号步骤，而不是怀疑自己的实现。

      5.3 硬规则要可执行

      不要写「注意分页效率」这类抽象要求，写：

      5. 分页时必须读一页贴一页，不要读完所有页再一次性输出。

      5.4 命令块里不要并列多个调用

      反面教材（就是引起批量读取的原因）：

      file_read offset=1   limit=100
file_read offset=101 limit=100
file_read offset=201 limit=100

      模型会把它们当成一个序列。改成带箭头的循环描述，或者干脆只写第 1 步的调用 + 一句「读完再 offset=101」。

      6. 分页大小怎么定

      不要拍脑袋。模拟 file_read 的输出格式（行号: 内容，行间 \n，末尾 \n[Lines A-B of N]），按页统计最坏字节数：

      lines = open(cache, 'rb').read().split(b'\n')
for page in (50, 100, 120):
    worst = 0
    for s in range(0, len(lines), page):
        chunk = lines[s:s+page]
        out = b'\n'.join(f"{s+i+1}: ".encode() + l for i, l in enumerate(chunk))
        out += f"\n[Lines {s+1}-{s+len(chunk)} of {len(lines)}]".encode()
        worst = max(worst, len(out))
    print(page, worst)

      实测（当前缓存 post_t7472145.txt：15493 字节、231 行的中文帖）：

      每页行数 最坏单页字节 12000 上限下
      50 4250 安全，留约 65% 余量
      100 7540 安全，留约 37% 余量
      120 9322 安全但接近

      选 100 行。这个数字同时写进 SKILL.md，让模型不需要自己算。

      7. 验证清单

      改动落地前逐条实跑：

      • [ ] 短帖：stdout 与缓存 diff 为空
      • [ ] 长帖：首行是 path:，四行信息完整
      • [ ] 强制分流：INLINE_MAX=4000 时短帖也走 path: 分支
      • [ ] 分页实测：按 SKILL.md 给的 offset/limit 能读完全部行，尾注右边界等于总行数
      • [ ] 缓存命中（无网络）仍能输出
      • [ ] 未知参数报错退出，不被当成 URL
      • [ ] 边界：无标题、无图片、超长单行（本例最长单行 873 字节，远低于上限）

      8. 可迁移的结论

      1. 截断在运行时，不在脚本。 先确认上限的单位与截断方式，再决定怎么绕。
      2. 分页是通用工具的能力，不是每个脚本的义务。 脚本的职责是「把完整内容放到一个稳定路径」，然后告诉 agent 路径。
      3. 缓存即输出。 不要让内部表示（哨兵、转义、中间格式）泄漏到文件里；stdout == cache 是一条可以自动化验证的不变式。
      4. 分流阈值必须 ≤ 运行时上限，否则直出分支会被静默截断。 这条规则的深层原因是：分流设计的本质，是把「截断」从运行时黑盒搬到了脚本侧白盒——脚本量的是字节，运行时砍的也是字节，单位终于对齐了。如果脚本按字符、运行时按字节，阈值永远无法可靠地设，分流就是摆设。
      5. 小模型靠结构，不靠篇幅。 编号步骤 + 字面前缀判断 + 错误示范，比详细解释更有效。
      6. 页大小要量，不要猜。 用模拟输出格式的方式算最坏字节数。
