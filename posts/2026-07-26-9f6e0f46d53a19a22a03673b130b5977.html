      zeroclaw HistoryPrunerConfig 死代码分析

      分析日期：2026-07-25

      结论概要

      HistoryPrunerConfig 定义了 4 个字段，但运行时只有 2 个被实际读取，另外 2 个是死代码，写上去没有任何效果。

      字段使用分析

      ✅ 生效的字段

      字段 作用
      enabled: bool 开关，控制是否启用 pruning
      max_tokens: usize 压模型 max_context_tokens 的上限，触发 context overflow → 自动截断

      ❌ 死代码字段

      字段 状态
      keep_recent: usize 仅定义 + 默认值，无任何运行时代码读取
      collapse_tool_results: bool 仅定义 + 默认值，无任何运行时代码读取

      代码证据

      定义位置

      core/config/scattered_types.rs:133

      pub struct HistoryPrunerConfig {
    pub enabled: bool,
    pub max_tokens: usize,
    pub keep_recent: usize,
    pub collapse_tool_results: bool,
}

      唯一的使用位置

      core/context/schema.rs:3378-3383：

      if self.history_pruning.enabled && self.history_pruning.max_tokens > 0 {
    self.max_context_tokens = self
        .max_context_tokens
        .min(self.history_pruning.max_tokens)
}

      仅读取 enabled 和 max_tokens，用后者覆盖 max_context_tokens 上限。

      死代码确认方法

      在整个代码库 grep（排除定义自身和测试代码）：

      • keep_recent → 零命中
      • collapse_tool_results → 零命中

      没有任何修剪逻辑（history_pruner.rs / history_trim.rs）去读这两个字段。

      实际效果

      这个配置项的本质就是借 max_tokens 压 context window，跟直接设 max_context_tokens 没有区别。

      用户如果写：

      history_pruning:
  enabled: true
  max_tokens: 24000
  keep_recent: 5
  collapse_tool_results: true

      后两项纯属心理安慰 —— keep_recent=5 和 collapse_tool_results=true 完全被忽略。
