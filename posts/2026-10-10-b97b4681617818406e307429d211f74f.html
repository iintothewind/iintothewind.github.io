      AI 不是许愿机：五个决定输出质量的关键

      一、问题界定能力：AI 的上限是你，不是模型

      "会用 AI"常被误解成"会写 prompt"，但 prompt 只是载体。真正的分水岭在 prompt 之前——你有没有把问题界定清楚。

      flowchart LR subgraph A["❌ 许愿式"] direction TB A1["模糊的一句话<br/>帮我写个方案"] --> A2["AI 靠猜补全细节"] --> A3["看起来很专业<br/>用不上，返工"] end subgraph B["✅ 先界定，再下指令"] direction TB B1["聊清边界 / 范围 / 约束"] --> B2["写出完整工程指令"] --> B3["AI 执行，一次可用"] end

      许愿式提问把"界定问题"这份工作甩给了 AI，AI 只能猜。猜对是运气，猜错是常态。

      二、完整的工程指令：六个要素

      mindmap root((完整工程指令)) 背景 谁，在什么处境下 目标 要解决什么问题 当前阶段 已经做到哪一步 约束 不能碰的边界有哪些 输出格式 先结论后展开，800 字以内 验收标准 怎样才算做对了

      六个要素缺一个，AI 就要在那个位置上猜一次。猜的次数越多，输出离你的预期越远。你给的是许愿还是工程指令，决定了 AI 回你的是废话还是答案。

      三、信息四象限：最大的敌人是看不见的盲区

      quadrantChart title 信息四象限：AI 能不能用对，看你处在哪个象限 x-axis "没意识到" --> "意识到了" y-axis "没说出来" --> "说出来了" quadrant-1 "已知-已知" quadrant-2 "未知-已知" quadrant-3 "未知-未知" quadrant-4 "已知-未知" "你知道且说了，AI 直接能用": [0.85, 0.85] "隐性知识：你会但没意识到，没说，AI 只能猜": [0.15, 0.85] "盲区：无意识遗漏，翻车重灾区": [0.15, 0.15] "知道自己不知道，可以主动追问": [0.85, 0.15]
      • 已知-已知（你知道且说了的）：这是工程指令的六要素能覆盖的部分。
      • 已知-未知（你知道自己不知道的）：意识到了就能处理——直接问 AI，让它帮你扫盲。
      • 未知-已知（你不知道自己知道的）：隐性知识。比如业务员天天手动用 Excel 收集报价，但她说不出"报价"二字背后有哪些业务约束——她会，但她没意识到要说。
      • 未知-未知（你不知道自己不知道的）：真正的盲区。开发者输入 "freeze the code"，本意是暂停变更，AI 却删了生产库——他没说冻结范围和操作边界，因为他不知道自己漏了。

      前两类你处理得了，后两类会无意识遗漏。而恰恰是后两类，决定了你是第几次返工。

      四、一条约束链：盲区 → 理解深度 → 指令质量 → 输出质量

      flowchart LR A["🔍 看不见的盲区<br/>未知-未知 / 未知-已知"] -->|"设上限"| B["🧠 你对问题的理解深度"] B -->|"设上限"| C["📝 你能写出的指令质量"] C -->|"决定"| D["🤖 AI 的输出质量"] style A fill:#f9e2e2,stroke:#c00 style D fill:#e2f0e2,stroke:#090

      这条链只能从左往右突破：缩小盲区（让 AI 帮你扫盲、让 AI 反过来问你）→ 加深理解 → 写出好指令。模型再强，也只是在链条的最右端等你。左边没做功，右边的模型能力再强也传导不过来。

      五、Coding agent 没有改变软件工程的本质

      以我最近做的一个项目为例：两周前接到任务，给一家货运公司做内部订单管理系统。启动时只跟业务负责人开过会，听她讲了一遍日常工作——手动用 Excel 收集报价的流程，拿到一堆邮件、PDF、Excel，然后就没了。然后是很多天、很多轮：聊需求边界、业务范围、数据约束 → 需求文档 → 设计文档 → 数据建模 → UI mockup 改了三版 → API specs → 最后才让 coding agent 写代码。这条链走完，agent 才"不会轻易跑偏"。

      flowchart LR A["📋 需求<br/>边界 / 范围 / 约束<br/>跟干系人一轮轮聊"] --> B["📐 设计<br/>数据建模 / mockup / API specs"] B --> C["🧪 测试<br/>验收标准先行"] C --> D["💻 实现<br/>coding agent 写代码"] D --> E{"验证通过？"} E -->|"否"| A E -->|"是"| F["✅ 交付"] style D fill:#e8f0fe,stroke:#06c

      注意 coding agent 在图里的位置：它只负责"实现"这一格。而企业应用的复杂度根本不在"实现"——

      flowchart TB S1["业务员<br/>每天手动 Excel 收集报价"] --> R["📋 需求分析<br/>把各方诉求翻译成<br/>统一的数据模型与约束"] S2["管理层<br/>要报表，要管控"] --> R S3["终端用户<br/>要好用，不出错"] --> R S4["开发者<br/>要可维护，可扩展"] --> R R --> D["设计 → 测试 → 实现"]

      业务员、管理层、终端用户、开发者要的东西互相打架，coding agent 听谁的？它只能听那个把各方诉求翻译成统一约束的人。这个人，就是做工程的人。跳过"需求 → 设计 → 测试 → 实现"直接许愿，得到的不是一个系统，而是一个精致的幻觉——能跑、像样，但没人敢用。

      一句话收束： coding agent 把"实现"的成本打到了接近零，于是"实现"之前的每一步——界定问题、写工程指令、照亮盲区、走完需求设计测试实现——反而变得更值钱了。你越把工程做扎实，agent 越强；你跳过工程直接许愿，AI 就只会放大你的草率。
